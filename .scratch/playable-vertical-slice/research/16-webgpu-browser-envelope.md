# WebGPU-only browser envelope findings

**Research question.** What do current first-party browser, WebGPU, Three.js, and GPU documentation establish about the supported browser versions, required WebGPU features, device/GPU constraints, loading limits, and accessibility implications for this WebGPU-only Playable Vertical Slice?

**Research date.** 2026-08-17. This note updates the earlier stack survey's WebGL2 recommendation: the slice architecture is now explicitly **WebGPU-only**. It does not implement a renderer or choose the final product support promise; those decisions belong to ticket 19.

## Executive findings

1. WebGPU is not a universal browser capability. A viable launch path must check `navigator.gpu`, request an adapter, handle a `null` adapter, inspect the adapter's features and limits, request a device, and configure a `webgpu` canvas. WebGPU requires a secure context; production therefore needs HTTPS (local development may use a trustworthy `localhost` origin). [MDN WebGPU API](https://developer.mozilla.org/en-US/docs/Web/API/WebGPU_API), [MDN secure contexts](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Secure_Contexts)
2. Browser support is platform- and version-specific. The current official overview records Chrome 113 desktop support on ChromeOS/Windows/macOS, Android support from Chrome 121 on Android 12+ devices with Qualcomm or ARM GPUs, Firefox 141 on Windows, and Safari 26 on Apple platforms. Current MDN browser-compatibility data adds partial/qualified cases (including Chrome 144 Linux Intel Gen12+ and Firefox Apple-silicon macOS from later versions) and records no Firefox Linux or Firefox Android support. This is a matrix to qualify, not a promise that a version number alone is sufficient. [Chrome for Developers WebGPU overview](https://developer.chrome.com/docs/web-platform/webgpu/overview), [MDN BCD GPU data (retrieved 2026-08-17)](https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/GPU.json), [Mozilla Firefox 141 notes](https://developer.mozilla.org/en-US/docs/Mozilla/Firefox/Releases/141), [WebKit Safari 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/)
3. Three.js `WebGPURenderer` currently has a WebGL2 fallback when WebGPU is unavailable. That is useful for a general Three.js app but violates this slice's WebGPU-only contract unless the app performs a fail-closed capability gate and never accepts the fallback backend. [Three.js `WebGPURenderer` API](https://threejs.org/docs/pages/WebGPURenderer.html), [Three.js `WebGPURenderer` source](https://github.com/mrdoob/three.js/blob/master/src/renderers/webgpu/WebGPURenderer.js)
4. Core WebGPU should be the baseline. Optional features (compressed texture formats, `shader-f16`, timestamp queries, subgroups, and others) vary by physical GPU, browser, and implementation, even when the hardware supports them. Request only features and limits the slice truly needs, after checking the adapter; otherwise device creation can fail. [MDN `GPUSupportedFeatures`](https://developer.mozilla.org/en-US/docs/Web/API/GPUSupportedFeatures), [MDN `GPUAdapter.requestDevice()`](https://developer.mozilla.org/en-US/docs/Web/API/GPUAdapter/requestDevice)
5. GPU resources are bounded by adapter-reported limits and browser privacy policy. Browsers may report tiered rather than exact values, so asset and shader budgets must fit the lowest qualified adapter rather than an assumed desktop GPU. [MDN `GPUSupportedLimits`](https://developer.mozilla.org/en-US/docs/Web/API/GPUSupportedLimits), [GPUWeb specification, limits and privacy considerations](https://gpuweb.github.io/gpuweb/)
6. Loading is asynchronous at two different layers: glTF/texture/decoder loading and GPU upload/initialization. Three.js exposes `loadAsync`, `LoadingManager` progress/error/abort hooks, and `Renderer.initTextureAsync()` specifically to move texture decode/upload cost out of the first visible render. The slice needs a visible boot/loading state and a bounded asset plan, not an assumption that a loaded URL is already GPU-ready. [Three.js `GLTFLoader`](https://threejs.org/docs/pages/GLTFLoader.html), [Three.js `LoadingManager`](https://threejs.org/docs/pages/LoadingManager.html), [Three.js `Renderer`](https://threejs.org/docs/pages/Renderer.html)
7. A canvas is a bitmap, not a semantic game interface: canvas-drawn objects are not exposed as semantic HTML to accessibility tools. The game must keep essential controls, state, instructions, and feedback in semantic DOM, with keyboard and simple-pointer alternatives to custom gestures, visible focus, non-color-only status, and reduced-motion behavior. [MDN `<canvas>`](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/canvas), [WCAG 2.2 Keyboard](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html), [WCAG 2.2 Pointer Gestures](https://www.w3.org/WAI/WCAG22/Understanding/pointer-gestures.html), [MDN `prefers-reduced-motion`](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion)

## Dated browser findings

### Chrome and Chromium/Edge

- Chrome's official overview says the initial WebGPU release was Chrome 113 on ChromeOS devices with Vulkan support, Windows devices with Direct3D 12 support, and macOS. It records Android support later in Chrome 121 for Android 12+ devices powered by Qualcomm and ARM GPUs. The same page links Firefox 141 and Safari 26 as later shipping implementations. [Chrome for Developers WebGPU overview](https://developer.chrome.com/docs/web-platform/webgpu/overview)
- Microsoft's first-party Open Source Blog records WebGPU as available by default in desktop Edge and Chrome 113 and Android Edge/Chrome 121. Treat that as a Chromium milestone, not proof that every Edge platform/GPU is usable. [Microsoft Open Source Blog](https://opensource.microsoft.com/blog/2024/02/29/onnx-runtime-web-unleashes-generative-ai-in-the-browser-using-webgpu/)
- Current MDN browser-compatibility data records Chrome 144 as a newer partial implementation for ChromeOS, macOS, Windows, and Linux limited by its note to Intel Gen12+ GPUs, with Chrome 113 as the older ChromeOS/macOS/Windows entry; it records Chrome Android 121. It mirrors Edge support and records Firefox 141 as partial, Safari 26, and no Firefox Android support. The data also notes Firefox macOS support is Apple-silicon-specific in later releases and that Firefox does not support Linux. Because this is a changing compatibility dataset, the product should keep a tested browser/OS/GPU matrix and runtime gate rather than using user-agent detection alone. [MDN BCD `GPU.json`](https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/GPU.json)
- **Envelope implication (recommendation).** A conservative public promise should name exact browser families, versions, operating systems, and GPU/driver qualification, and should list Linux and mobile separately. “WebGPU supported” is not equivalent to “this game's scene, shader, texture, and frame-time budget works.” This is a product recommendation derived from the platform matrix above.

### Firefox

- Firefox 141 (released 2025-07-22) documents WebGPU as fully supported on Windows in all contexts except service workers. [Firefox 141 developer notes](https://developer.mozilla.org/en-US/docs/Mozilla/Firefox/Releases/141)
- Mozilla's Graphics Team describes Firefox 141 WebGPU as shipping on Windows and calls out that support is not yet equivalent across other platforms. [Mozilla Graphics Team: Shipping WebGPU on Windows in Firefox 141](https://mozillagfx.wordpress.com/2025/07/15/shipping-webgpu-on-windows-in-firefox-141/)
- Current MDN BCD records Firefox 145 for macOS Tahoe on Apple silicon, Firefox 147 for older macOS on Apple silicon, no Intel-macOS support, no Linux support, and no Firefox Android support. [MDN BCD `GPU.json`](https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/GPU.json)
- **Constraint.** If Firefox is promised, the initial acceptance matrix should be Windows first; Apple-silicon macOS support must be qualified against the chosen Firefox release. Worker/service-worker assumptions must not be generalized from Window support.

### Safari/WebKit

- WebKit documents WebGPU shipping in Safari 26.0 for macOS, iOS, iPadOS, and visionOS. It describes WGSL as the shader language and says WebGPU maps to Metal on those platforms. [WebKit Safari 26.0 WebGPU section](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/)
- The earlier WebKit Safari 26 beta announcement identifies the same Apple-platform scope and notes that Three.js works with WebGPU in Safari 26 beta. [WebKit Safari 26 beta](https://webkit.org/blog/16993/news-from-wwdc25-web-technology-coming-this-fall-in-safari-26-beta/#webgpu)
- **Constraint.** Safari 26 is a real target, but its OS-tied versioning and Apple GPU/driver combinations make it a separate qualification lane. The product must decide whether iOS/iPadOS are in scope: WebGPU availability does not make the desktop-sized scene, controls, memory use, or performance budget suitable for every phone/tablet.

## WebGPU initialization and device contract

The normative/first-party API shape establishes the following boot contract:

1. Check `navigator.gpu` (or `WorkerNavigator.gpu` in a worker) and fail with a player-readable unsupported-browser screen if absent. `GPU`/`WorkerNavigator.gpu` are secure-context features. [MDN WebGPU API](https://developer.mozilla.org/en-US/docs/Web/API/WebGPU_API), [MDN `WorkerNavigator.gpu`](https://developer.mozilla.org/en-US/docs/Web/API/WorkerNavigator/gpu)
2. Call `navigator.gpu.requestAdapter()` and handle `null`: the user agent chooses whether to expose a suitable adapter, and an adapter may simply be unavailable. [MDN `GPU.requestAdapter()`](https://developer.mozilla.org/en-US/docs/Web/API/GPU/requestAdapter)
3. Inspect `adapter.features` and `adapter.limits`. A browser may withhold a feature even when the physical hardware has it; limits are implementation/adapter values, and browsers can report privacy-preserving tiers instead of exact physical values. [MDN `GPUSupportedFeatures`](https://developer.mozilla.org/en-US/docs/Web/API/GPUSupportedFeatures), [MDN `GPUSupportedLimits`](https://developer.mozilla.org/en-US/docs/Web/API/GPUSupportedLimits), [GPUWeb specification](https://gpuweb.github.io/gpuweb/)
4. Request a device with the smallest tested `requiredFeatures` and `requiredLimits` set. Unsupported required features reject with `TypeError`; unsupported or too-high limits reject with `OperationError`. [MDN `GPUAdapter.requestDevice()`](https://developer.mozilla.org/en-US/docs/Web/API/GPUAdapter/requestDevice)
5. Configure the canvas using `getContext('webgpu')`, `navigator.gpu.getPreferredCanvasFormat()`, and the selected device. The preferred format is intended to select the efficient `bgra8unorm` or `rgba8unorm` choice for the device. [MDN WebGPU API](https://developer.mozilla.org/en-US/docs/Web/API/WebGPU_API)
6. Attach device loss and error handling before presenting gameplay. `GPUDevice.lost` resolves if the device is lost; losses can be transient, but all resources from the old device must be recreated, and an adapter can become unavailable. [MDN `GPUDevice.lost`](https://developer.mozilla.org/en-US/docs/Web/API/GPUDevice/lost), [MDN `GPUDevice.pushErrorScope()`](https://developer.mozilla.org/en-US/docs/Web/API/GPUDevice/pushErrorScope)

### GPU and power constraints

- `requestAdapter({ powerPreference })` is a hint, not a guarantee. `low-power` favors battery life; `high-performance` may choose a discrete GPU, increase battery use, and increase device-loss risk when the system switches adapters. [MDN `GPU.requestAdapter()`](https://developer.mozilla.org/en-US/docs/Web/API/GPU/requestAdapter)
- A fallback adapter can be software-backed and have significant performance caveats; it may not exist on every system. The API exposes fallback status through `GPUAdapterInfo.isFallbackAdapter` where supported. Whether fallback is permitted must be an explicit product decision because a WebGPU API success alone does not establish game performance. [MDN `GPU.requestAdapter()`](https://developer.mozilla.org/en-US/docs/Web/API/GPU/requestAdapter), [MDN `GPUAdapterInfo.isFallbackAdapter`](https://developer.mozilla.org/en-US/docs/Web/API/GPUAdapterInfo/isFallbackAdapter)
- WebGPU's security and validation model deliberately mediates access to the physical GPU; the app cannot treat a physical GPU's native capabilities as directly available. [GPUWeb specification](https://gpuweb.github.io/gpuweb/), [WebKit Safari 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/)
- **Recommendation.** Make core WebGPU rendering the hard requirement, but treat compressed texture formats, `shader-f16`, subgroups, timestamp queries, and other optional features as capability branches. Avoid making one optional feature a launch blocker unless ticket 19 intentionally narrows the browser/device promise.

## Three.js-specific constraints

- Three.js documents `WebGPURenderer` as an alternative to `WebGLRenderer`, but its default behavior falls back to a WebGL 2 backend when WebGPU is unavailable. The source explicitly installs a fallback callback. For this project, preflight `navigator.gpu`, initialize the renderer asynchronously, verify the selected backend/initialization result, and show an unsupported state rather than allowing the fallback. [Three.js `WebGPURenderer` API](https://threejs.org/docs/pages/WebGPURenderer.html), [Three.js source](https://github.com/mrdoob/three.js/blob/master/src/renderers/webgpu/WebGPURenderer.js), [Three.js `Renderer.init()`](https://threejs.org/docs/pages/Renderer.html)
- Three.js `Renderer.init()` is asynchronous; `render()` requires an initialized renderer except when the animation-loop path guarantees initialization. This creates a real boot boundary for device setup, shader/pipeline setup, and initial assets. [Three.js `Renderer`](https://threejs.org/docs/pages/Renderer.html)
- `GLTFLoader` is an addon imported separately and loads glTF 2.0. It supports Draco, meshopt, KTX2/Basis, WebP/AVIF, and related extensions, but decoder-backed extensions require their corresponding decoder/loader configuration. Its documentation warns that image bitmaps are not automatically garbage-collected when no longer referenced and require explicit disposal handling. [Three.js `GLTFLoader`](https://threejs.org/docs/pages/GLTFLoader.html)
- `LoadingManager` exposes start/progress/load/error callbacks and an abort operation; abort only works for loaders that implement the abort path and where `AbortSignal.any()` is supported. Use it for a real loading screen, cancellation on Scene change, and actionable error reporting, not as proof that GPU upload has completed. [Three.js `LoadingManager`](https://threejs.org/docs/pages/LoadingManager.html)
- `Renderer.initTextureAsync()` exists to preload texture decode/upload so first use does not cause a noticeable lag. The game should separate “network/decoder loaded” from “GPU resources initialized.” [Three.js `Renderer`](https://threejs.org/docs/pages/Renderer.html)
- **WebGPU-only implication.** Do not use the earlier survey's `WebGLRenderer` compatibility baseline and do not silently use `forceWebGL`. Pin and qualify a Three.js version because the official Chrome overview still describes Three.js WebGPU support as in progress, while Three's current API exposes an evolving WebGPU renderer. [Chrome for Developers WebGPU overview](https://developer.chrome.com/docs/web-platform/webgpu/overview), [Three.js `WebGPURenderer`](https://threejs.org/docs/pages/WebGPURenderer.html)

## Loading, memory, and presentation limits

- GPU limits are per adapter and can be privacy-tiered. The reference defaults include (among others) `maxTextureDimension2D` 8192, `maxTextureArrayLayers` 256, `maxBindGroups` 4, `maxUniformBufferBindingSize` 64 KiB, and `maxBufferSize` 256 MiB; these are not a portable game budget, because browser-reported values and implementation tiers can vary. Query the adapter and test the lowest promised tier. [MDN `GPUSupportedLimits`](https://developer.mozilla.org/en-US/docs/Web/API/GPUSupportedLimits)
- Optional compression features are not universal. Three.js can load compressed glTF assets through decoder addons, but the eventual GPU texture format still has to be supported by the selected device/feature set. Keep a compatible texture path or gate the asset variant after capability detection. [Three.js `GLTFLoader`](https://threejs.org/docs/pages/GLTFLoader.html), [MDN `GPUSupportedFeatures`](https://developer.mozilla.org/en-US/docs/Web/API/GPUSupportedFeatures)
- The HTML canvas maximum dimensions are browser/environment dependent; MDN specifically notes iOS devices limiting canvas size to 4096×4096 and says exceeding the maximum makes the canvas unusable. Set a conservative drawing-buffer/DPR cap instead of multiplying an arbitrary CSS size by device pixel ratio. [MDN `<canvas>`](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/canvas)
- Cross-origin model, texture, decoder, and font URLs are subject to the browser same-origin policy. Cross-origin script/fetch resources need the server's CORS permission; CORS failures surface to script only as a generic error. Prefer same-origin packaged assets for the slice or configure and monitor CORS explicitly. [MDN CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS)
- An OffscreenCanvas can be transferred to a worker, and WebGPU's `WorkerNavigator.gpu` is exposed in workers in secure contexts. This can keep simulation/UI responsive, but Firefox's release note exception for service workers means a service worker must not be assumed to be a rendering host. Worker rendering is an implementation option, not a requirement for the slice. [MDN OffscreenCanvas](https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas), [MDN `WorkerNavigator.gpu`](https://developer.mozilla.org/en-US/docs/Web/API/WorkerNavigator/gpu), [Firefox 141 developer notes](https://developer.mozilla.org/en-US/docs/Mozilla/Firefox/Releases/141)

## Accessibility implications

### Canvas and semantic UI

- MDN states that canvas content is a bitmap and is not exposed to accessibility tools as semantic HTML; it recommends alternate content and warns that canvas alone is generally not an accessible website/app surface. [MDN `<canvas>`](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/canvas)
- The game therefore needs a DOM accessibility layer around the WebGPU canvas: semantic buttons/menus, headings and instructions, text labels for Band/Agent state, a live/status region for commands and consequential outcomes, and an accessible unsupported/loading/error screen. This is a design recommendation based on the canvas limitation and WCAG criteria, not a claim that WebGPU supplies UI semantics.

### Input and control equivalence

- WCAG 2.2 SC 2.1.1 requires all functionality to be operable through a keyboard interface, except where the underlying function inherently depends on a path. The four-sector guard/command gestures therefore need an equivalent keyboard or semantic-control mode, with no requirement for precise timed keystrokes. [W3C WCAG 2.2 Keyboard](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html)
- WCAG 2.2 SC 2.5.1 requires a single-pointer, non-path alternative for multipoint/path-based gestures unless the gesture is essential. Provide click/tap sector buttons or a selectable command mode in addition to drag/swipe gestures; do not make a path gesture the only way to guard, command, or confirm. [W3C WCAG 2.2 Pointer Gestures](https://www.w3.org/WAI/WCAG22/Understanding/pointer-gestures.html)
- Use real HTML controls where possible so focus, name, role, and keyboard activation are provided by the platform. Keep focus visible and ensure the DOM controls remain usable when the canvas is paused, loading, loses the device, or is covered by an error overlay. These are implementation implications of WCAG 2.1.1 and the semantic-canvas limitation.

### Visual, motion, and feedback baseline

- WCAG 2.2 covers accessibility for blindness/low vision, deafness/hearing loss, limited movement, photosensitivity, and cognitive limitations; the game should treat graphics as enhancement rather than the only channel for game state. [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/)
- Do not communicate guard direction, health, Disposition, Fate, or command result by color alone; pair color with text, icons, shape, or position and expose the same state in DOM text. Relevant criteria include [WCAG 1.1.1 Non-text Content](https://www.w3.org/WAI/WCAG22/Understanding/non-text-content.html), [WCAG 1.4.1 Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html), and [WCAG 1.4.3 Contrast (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).
- Honor `prefers-reduced-motion`: the browser exposes it as a user preference to remove, reduce, or replace non-essential motion, and MDN calls out scaling/panning as possible vestibular triggers. Offer reduced camera shake, hit flashes, screen motion, and animation intensity without changing simulation outcomes. [MDN `prefers-reduced-motion`](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion)
- Provide pause/stop controls for non-essential moving UI and avoid flashes; treat combat animation, camera shake, and transient feedback as potentially accessibility-relevant rather than merely cosmetic. Ticket 19 should choose the promised accessibility level (for example, a WCAG-informed baseline versus a formal conformance target) and document any intentionally excluded real-time interaction.

## Constraints to expose to the player

The startup and runtime UI should expose, in plain language:

- WebGPU unavailable or blocked (including non-HTTPS deployment), with a supported-browser link rather than a blank canvas. [MDN WebGPU API](https://developer.mozilla.org/en-US/docs/Web/API/WebGPU_API)
- Adapter unavailable, required feature/limit mismatch, or device initialization failure. [MDN `GPU.requestAdapter()`](https://developer.mozilla.org/en-US/docs/Web/API/GPU/requestAdapter), [MDN `GPUAdapter.requestDevice()`](https://developer.mozilla.org/en-US/docs/Web/API/GPUAdapter/requestDevice)
- Device loss and whether the game is retrying, returning to a safe checkpoint, or requiring reload. [MDN `GPUDevice.lost`](https://developer.mozilla.org/en-US/docs/Web/API/GPUDevice/lost)
- Asset download/decode/GPU-upload progress and a recoverable load error. [Three.js `LoadingManager`](https://threejs.org/docs/pages/LoadingManager.html), [Three.js `Renderer`](https://threejs.org/docs/pages/Renderer.html)
- Keyboard and pointer alternatives, reduced-motion state, and any accessibility mode selected by the player. [W3C WCAG 2.2 Keyboard](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html), [W3C WCAG 2.2 Pointer Gestures](https://www.w3.org/WAI/WCAG22/Understanding/pointer-gestures.html), [MDN `prefers-reduced-motion`](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion)

## Unresolved product decisions for ticket 19

1. **Browser/device target.** Which exact browser families and minimum versions are promised: Chromium desktop (and which OSes), Edge, Firefox Windows and/or Apple-silicon macOS, Safari 26 Apple platforms, Android, and Linux? Is a fallback/software adapter rejected, or is it allowed if it meets the measured frame-time budget? The evidence supports a tested matrix, not a single universal “WebGPU browser” claim.
2. **GPU/driver floor.** What scene complexity, resolution, device-pixel-ratio cap, texture dimensions/format, optional-feature set, and adapter limits define the lowest supported tier? Will the slice require only core WebGPU, or require a compressed texture feature/`shader-f16`/other optional feature? What happens when a device has WebGPU but misses the budget?
3. **Performance promise.** Choose target and minimum frame-rate budgets, frame-time percentile, startup-to-first-frame and Scene-transition loading budgets, memory/asset budgets, and behavior under battery/low-power adapters. Decide whether `powerPreference: 'high-performance'` is allowed on laptops/mobile or whether battery preservation wins.
4. **Loading behavior.** Decide whether the initial boot downloads all slice assets or streams/loads per Scene; the maximum acceptable loading screen duration; whether compressed glTF/texture variants are shipped; whether same-origin hosting is required; whether a retry, asset-quality downgrade, or a terminal unsupported state is used after failure; and whether rendering/simulation moves to a worker.
5. **Device-loss behavior.** Choose whether to retry and recreate the renderer/resources, return to the last safe checkpoint, pause with a recoverable message, or require a reload. Decide how much state is persisted before retry and how to report GPU validation/out-of-memory errors without exposing technical jargon.
6. **Accessibility baseline.** Choose the promised WCAG-informed level and scope: semantic DOM controls and text state for all essential actions, keyboard-equivalent combat/commands, single-pointer alternatives, color-independent status, visible focus, reduced-motion mode, pause/stop behavior, captions/transcripts for audio cues, and screen-reader announcement policy. Decide which real-time/path-dependent interactions (if any) are genuinely essential and what equivalent the player receives.
7. **Evidence matrix.** Select the concrete browser/OS/GPU combinations and accessibility settings (keyboard-only, reduced motion, high contrast/zoom where applicable) that must pass before the support promise is published. This should include a WebGPU-unavailable case and a device-loss/load-failure case.
